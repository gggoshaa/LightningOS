# LightningOS v1.0.0.0 "Thunderbolt"

Маленькая 32-битная операционная система для x86, написанная с нуля:
загрузчик на ассемблере (NASM) + ядро на C. Работает на «голом железе»,
без каких-либо библиотек и без хост-ОС под собой.

## Что уже работает

| Подсистема | Описание |
|---|---|
| Загрузчик | Свой MBR на 512 байт: читает ядро через BIOS INT 13h (LBA), получает карту памяти через INT 15h/E820, включает A20, переходит в 32-битный protected mode |
| Ядро | Флэт-модель памяти, собственные GDT и IDT, обработчики всех 32 исключений CPU |
| Многозадачность | Вытесняющий планировщик, round-robin по тику PIT, задачи ядра со своими стеками |
| Прерывания | Ремап PIC на векторы 0x20/0x28, диспетчер IRQ с регистрацией обработчиков и управлением масками |
| Память | Разбор карты E820, куча ядра на 32 МиБ, `kmalloc`/`kfree` со слиянием свободных блоков |
| Консоль | VGA 80x25 с цветом, аппаратным курсором и **512 строками скроллбэка** |
| Ввод | PS/2 клавиатура (IRQ1) и PS/2 мышь-колесо (IRQ12, IntelliMouse 4-байтные пакеты) |
| Драйверы | PIT-таймер 100 Гц, CMOS RTC, COM1 |
| Диск | Драйвер ATA PIO (LBA28) с опросом, без DMA и без IRQ14 |
| Файловая система | `ramfs` — иерархическая ФС в памяти с Unix-путями, со снимком на диск |
| Постоянное хранение | Снимок дерева и учётных записей на отдельном диске данных, с контрольной суммой |
| Пользователи | Мастер первоначальной настройки, вход по логину и паролю, `su`, `passwd`, `useradd`/`userdel`, права на запись |
| Оболочка | `lsh` — история команд, редактирование строки, ~35 встроенных команд |
| Паника | Красный экран с дампом регистров и адресом page fault |
| Установка | Загрузочный ISO (El Torito) с установщиком: запись системы на жёсткий диск или живой режим |

## Версия

Версия записана **в одном месте** — `LOS_VERSION` в `include/version.h`.
Оттуда её берут и ядро, и `build.py`, поэтому для выпуска новой версии
достаточно поменять эту строку.

Версию видно в загрузочной строке, в баннере, в заголовке установщика, в
мастере первичной настройки, в приглашении входа, в `uname -a`, в файле
`/etc/version` и в команде `version`:

```
root@lightning:~# version
LightningOS v1.0.0.0 "Thunderbolt"

  Version      : 1.0.0.0
  Codename     : Thunderbolt
  Architecture : i386, 32-bit protected mode
  Built        : 2026-09-17T19:25
  Kernel image : 55360 bytes in 109 sectors
  Booted from  : a hard disk
  Source       : https://github.com/gggoshaa/LightningOS
```

ISO собирается сразу с версией в имени файла — `build/lightningos-1.0.0.0.iso`,
его можно без переименования прикладывать к релизу на GitHub. Метка тома тоже
содержит версию (`LIGHTNINGOS_1_0_0_0`), так что определить, какой образ перед
вами, можно не загружая его.

## Установочный ISO

`build.py` собирает два образа: жёсткого диска и **загрузочный ISO с
установщиком**.

```
python run.py --iso          загрузиться с установщика (пустой диск-цель)
python run.py --installed    загрузить то, что установщик записал
python run.py                собранная система на двух дисках (режим разработки)
```

Загрузившись с ISO, вы попадаете в меню: поставить систему на жёсткий диск,
попробовать без установки или перезагрузиться. Установщик показывает целевой
диск и точную раскладку записи, требует подтверждения `YES`, и пишет три вещи:
загрузочный сектор, ядро и пустую область данных.

Живой режим намеренно **не трогает диск**: пока система запущена с
установочного носителя, сохранение отключено целиком. Начинать писать на чужой
жёсткий диск без спроса было бы неправильно.

### Как загружается ISO

Обычному загрузчику с CD нужен драйвер диска. Здесь он не нужен вовсе: в
каталоге загрузки El Torito указан **сегмент загрузки 0x0FE0**, поэтому BIOS
сам кладёт весь образ (загрузочный сектор CD плюс ядро) по адресу `0xFE00` —
а значит ядро оказывается ровно по `0x10000`, там же, куда его прочитал бы
загрузчик с жёсткого диска. `boot/cdboot.asm` остаётся только получить карту
памяти, включить A20 и перейти в protected mode.

ISO 9660 и запись El Torito пишет `tools/makeiso.py` — минимальный, но
корректный образ: есть первичный дескриптор тома, таблицы путей, корневой
каталог и `README.TXT`, так что диск монтируется обычной системой.

### Откуда установщик берёт то, что пишет

Скопировать загрузочный сектор из памяти нельзя: при загрузке с CD первый
сектор образа — это стадия El Torito, а не та, что нужна жёсткому диску.
Поэтому настоящий загрузочный сектор едет внутри ядра как массив байтов
(`kernel/bootsector.c` генерируется при сборке из `boot/boot.asm`).

Само ядро уже лежит в памяти — это ровно то, что загрузчик положил по
`0x10000`. Но записывать работающий образ можно только пока он не изменён,
поэтому чистая копия снимается в самом начале `kmain`, сразу после
`mem_init()`, до того как что-либо успевает тронуть `.data`.

### Раскладка установленного диска

```
сектор 0        загрузочный сектор
сектор 1..N     ядро
сектор 2048..   область данных (тот же формат снимка)
```

Слой хранения при загрузке пробует обе раскладки: сначала отдельный диск
данных (primary slave, сектор 0), затем область на загрузочном диске.
Найденный снимок всегда в приоритете. Команда `df` показывает, что выбрано.

## Многозадачность

Планировщик **вытесняющий**: задачу снимают с процессора по тику таймера,
не спрашивая её согласия.

Ключ к простоте — в том, что заглушка обработчика прерывания уже кладёт весь
набор регистров на стек той задачи, которую прервали. Значит контекст задачи
целиком описывается одним числом: её указателем стека. Переключение — это
просто возврат на другом стеке, поэтому диспетчеры в `idt.c` *возвращают*
указатель стека, а ассемблерная заглушка загружает его через `mov esp, eax`.

Новая задача получает поддельный кадр прерывания на вершине своего стека,
так что первый же `iret` попадает в её точку входа. Вход идёт через C-обёртку,
чтобы задача, которая просто вернулась из своей функции, всё равно была
корректно завершена.

Что есть:

- задачи ядра со своим стеком по 16 КиБ (все в ring 0, одно адресное
  пространство — страничной организации ещё нет);
- `task_sleep_ms()` — спящая задача не отнимает у планировщика ничего;
- `task_yield()` через программное прерывание `0x30` — задача отдаёт процессор
  сразу, не дожидаясь тика;
- задача `idle`, которая работает только когда больше некому, и заодно
  освобождает стеки завершившихся задач;
- `ps`, `spawn`, `kill` в оболочке.

Оболочка живёт в задаче `session`. Пока она ждёт нажатия клавиши, она **спит**,
а не крутит опрос, поэтому в простое занимает 0% процессора.

Посмотреть вживую:

```
spawn worker 25      # задача, жгущая CPU, на 25 секунд
spawn worker 25
spawn ticker 30      # задача, которая только спит
ps                   # воркеры делят CPU поровну, ticker и session на нуле
```

Оболочка при этом остаётся полностью отзывчивой — в этом и весь смысл.

### Общие данные

Куча и консоль теперь доступны из нескольких задач, поэтому критические секции
в `kmalloc`/`kfree` и `vga_putc` закрыты маскированием прерываний (`lock.h`).
На однопроцессорной машине, где вытеснение приходит только от таймера, это
полноценный мьютекс: пока прерывания закрыты, больше выполняться нечему.

## Хранение данных

Дисков два, и это принципиально:

| Диск | Что на нём | Кто его трогает |
|---|---|---|
| 0, primary master | `build/lightningos.img` — загрузчик и ядро | пересоздаётся при каждой сборке |
| 1, primary slave | `build/data.img` (или `data.vdi`) — данные | создаётся один раз, больше никогда не перезаписывается |

Благодаря разделению пересборка ядра не стирает то, что система успела
сохранить. Диск данных создаётся автоматически при первом запуске.

Хранение сделано **снимком, а не блочной ФС**: всё дерево вместе с таблицей
учётных записей сериализуется в один непрерывный участок секторов. Дерево
занимает килобайты, поэтому переписать его целиком — это несколько PIO-передач,
зато не нужны ни аллокатор блоков, ни журнал, ни решение задач целостности,
которые они за собой тянут.

Раскладка на диске данных:

```
LBA 0        суперблок: magic, версия, длина, счётчик узлов, FNV-контрольная сумма
LBA 1 .. N   полезная нагрузка: учётные записи, затем узлы дерева в порядке обхода
```

Сначала пишется нагрузка и только потом суперблок: если питание пропадёт
посередине, старый суперблок по-прежнему указывает на целую старую нагрузку,
а порванная запись ловится контрольной суммой. При несовпадении система
честно сообщает об этом и продолжает работать в памяти, не затирая диск.

Снимок записывается **после каждой изменяющей команды**, а также по `sync`,
`reboot` и `shutdown`. Команда `df` показывает диски и заполнение.

`mkfs` (от root) стирает диск данных, спрашивает подтверждение `YES` и
**сразу перезагружает машину**. Это не удобство, а необходимость: после
стирания старое дерево и учётные записи всё ещё живут в памяти, и любое
следующее сохранение записало бы их обратно, отменив стирание. На случай,
если до перезагрузки что-то всё же попробует записать, слой хранения после
`mkfs` «запечатывается» и `persist_save()` отказывается работать до
следующей загрузки.

Лимит снимка — 1 МиБ. Если дерево его перерастёт, `sync` честно скажет об этом,
а не запишет обрезанные данные.

## Пользователи и первоначальная настройка

При первой загрузке запускается мастер: он просит задать пароль для `root`
и предлагает завести обычную учётную запись. Дальше система выходит на
приглашение входа `lightning login:` — пароль вводится скрытно.

Права устроены просто, но по-настоящему: `root` пишет куда угодно, обычный
пользователь — только в свой домашний каталог и в `/tmp`. Попытка записать
в `/etc` вернёт `permission denied`. Путь проверяется по родительскому
каталогу, поэтому обойти проверку через `..` нельзя.

`/etc/passwd` не статичный файл — он генерируется из таблицы учётных записей,
так что `cat /etc/passwd` всегда показывает реальное состояние.

Мастер запускается только тогда, когда учётных записей нет — то есть при
первой загрузке или после `mkfs`. Если снимок на диске есть, система сразу
выходит на приглашение входа.

> **Важно про пароли.** Хэш — это FNV-1a с солью и 4096 раундов перемешивания,
> то есть 32 бита. Это защита от подглядывания в память, а **не** криптография:
> такой хэш не устоит против перебора. К тому же снимок на диске не зашифрован,
> так что доступ к файлу `data.img` равносилен доступу к хэшам.

## Прокрутка экрана

Колесо мыши листает историю вывода (512 строк). Драйвер включает режим
IntelliMouse «магическим стуком» — последовательностью частот опроса
200/100/80, после которой мышь начинает присылать четвёртый байт с осью Z.
Если мыши нет, работают `PageUp` и `PageDown`. Любой новый вывод возвращает
экран вниз, а `clear` не уничтожает историю, а складывает экран в неё.

Команда `lsdev` показывает, определилось ли колесо.

## Сборка и запуск

```
python build.py        # собирает build/lightningos.img
python run.py          # запускает образ на эмуляторе
```

Либо просто `run.bat` — он сделает и то, и другое.

### Что требуется

Ассемблер — NASM. Компилятор C — либо полный LLVM, либо Zig (в нём внутри
тот же clang + lld + objcopy, но он портативный и весит на порядок меньше;
`build.py` сам определит, что установлено):

```
winget install NASM.NASM
winget install zig.zig          # либо LLVM.LLVM, если есть ~4 ГБ свободных
```

Для запуска `run.py` использует QEMU, а если его нет — VirtualBox
(создаёт одноразовую VM из образа полностью из командной строки):

```
winget install SoftwareFreedomConservancy.QEMU   # опционально, ~1.5 ГБ
```

### Полезные варианты запуска

```
python run.py --headless        # без окна; экран снимается скриншотом
python run.py --reset-data      # стереть диск данных и начать с чистого листа
python run.py --reset-target    # стереть диск, на который ставит установщик
python run.py -serial stdio     # QEMU: дублировать вывод ядра в терминал
python run.py -s -S             # QEMU: ждать подключения gdb на :1234
```

Под VirtualBox кэш хоста для IDE-контроллера намеренно выключен
(`--hostiocache off`). С включённым кэшем VirtualBox держит записи гостя в
памяти хоста, и жёсткое `controlvm poweroff` их теряет: гость уверен, что
снимок записан, а в VDI он так и не попал. Изнутри системы всегда лучше
выходить через `shutdown`.

В headless-режиме под VirtualBox экран и питание управляются так:

```
VBoxManage controlvm LightningOS screenshotpng shot.png
VBoxManage controlvm LightningOS keyboardputstring "uname -a"
VBoxManage controlvm LightningOS poweroff
```

## Команды оболочки

```
система:    help  uname -a  version  banner  clear  history  color  free
            meminfo  lsdev  df  sync  uptime  date  sleep
задачи:     ps  spawn  kill  yield
файлы:      ls  tree  cd  pwd  cat  echo  mkdir  touch  rm
учётки:     whoami  id  users  su  passwd  useradd  userdel  logout
диск:       df  sync  mkfs (от root, стирает диск данных)
питание:    reboot  shutdown (он же poweroff / halt)
```

`echo` умеет перенаправление: `echo привет > note.txt`, `echo ещё >> note.txt`.
Ctrl-L очищает экран, Ctrl-C отменяет строку, Ctrl-U стирает её целиком,
стрелки вверх/вниз листают историю команд.

`shutdown` выключает машину через ACPI: запись в порт 0x604 (QEMU), 0xB004
(Bochs) или 0x4004 (VirtualBox) — какой из них сработает, зависит от гипервизора.

## Структура проекта

```
boot/boot.asm        загрузчик с жёсткого диска (512 байт)
boot/cdboot.asm      загрузчик с CD, El Torito (512 байт)
kernel/entry.asm     точка входа ядра, обнуление .bss, вызов kmain
kernel/interrupt.asm заглушки ISR/IRQ и вектор yield (генерируются скриптом)
kernel/kernel.c      kmain и последовательность загрузки
kernel/gdt.c         таблица дескрипторов
kernel/idt.c         таблица прерываний, PIC и маски IRQ
kernel/mem.c         карта памяти и куча
kernel/task.c        планировщик и переключение контекста
kernel/console.c     редактор строки и история (общий для оболочки и логина)
kernel/users.c       учётные записи, вход, мастер настройки, права
kernel/shell.c       оболочка lsh
kernel/banner.c      логотип (генерируется, не править руками)
kernel/install.c     установщик: снимок образа, запись на диск, меню
kernel/bootsector.c  загрузочный сектор как данные (генерируется при сборке)
kernel/panic.c       kernel panic
drivers/             vga (со скроллбэком), keyboard, mouse, ata, timer, rtc, serial
fs/ramfs.c           файловая система в памяти
fs/persist.c         снимок дерева и учёток на диск данных
lib/                 string.c и printf.c (своя мини-libc)
linker.ld            скрипт компоновки, ядро по адресу 0x10000
tools/makeiso.py     генератор ISO 9660 с записью El Torito
build.py             сборка образа диска и ISO
run.py               запуск в QEMU или VirtualBox
```

## Как это загружается

1. BIOS читает первый сектор образа по адресу `0x7C00` и передаёт управление.
2. Загрузчик запрашивает карту памяти (E820) и кладёт её по адресу `0x8000`.
3. 256 секторов (128 КиБ) ядра читаются по адресу `0x10000`.
4. Включается линия A20, грузится временная GDT, взводится `CR0.PE`.
5. Дальний переход в 32-битный код, затем прыжок на `0x10000`.
6. `_start` обнуляет `.bss`, ставит стек на 32 КиБ и зовёт `kmain()`.

## Ограничения

Осознанно не сделано: страничная организация памяти, пользовательский режим
(ring 3 дескрипторы в GDT есть, но системных вызовов нет), разделы и таблица
разделов. Многозадачность есть, но задачи живут в ring 0 и делят одно
адресное пространство: изоляции между ними нет, а приоритетов и вытеснения
по приоритету — тоже (round-robin с равными квантами). Разделение прав работает на уровне оболочки, а не
ядра: пока всё исполняется в ring 0, это соглашение, а не аппаратная защита.
Хранение — снимок целиком, поэтому стоимость записи зависит от размера всего
дерева, а не от размера изменения; для дерева в килобайты это незаметно, но
масштабироваться такой подход не будет.
